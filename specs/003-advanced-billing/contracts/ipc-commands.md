# Contract: commands added or changed by feature 003

Rules as in `specs/001-shop-os-mvp/contracts/ipc-commands.md` (result shape, paise and thousandths, shared Zod schemas, no database in the renderer). Approvals come from feature 005: a command that needs one returns `APPROVAL_REQUIRED` with `{ kind, amountPaise, subject }`; the screen asks for a PIN through `approvals.requestAtCounter` (005) and calls again with the `approvalId`.

All 001 guarantees hold for `bills.save` and `bills.edit`: one transaction (version row, lines, tenders, movements including `edit_reverse`, ledger entries through 004, audit row through 005, approvals consumed, UPI references claimed in `upi_reference`), idempotent by `clientBillId`, committed before print or share.

**Quotation quantities**: `quotes.prepareBill` only drafts. `bills.save` and `bills.edit` check again, inside the save transaction and with current unit conversions, that each referenced `quotationLineId` still has open quantity for the **sum** of the save's lines that reference it (two lines of 6 against 10 open take 12 and are refused); otherwise they return `QUOTE_LINE_OVERDRAWN` and write nothing. So two drafts from one quote cannot both overdraw it. Example: quote line 10 pcs, a saved bill took 6; a second draft for 6 is refused at save.

## Tenders

| Command              | Input                                         | Result                                                                                  | Error codes                                                                                              |
| -------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `tenders.upiIntent`  | `{ amountPaise, billNo? }`                    | `{ intentUrl, qrSvg }`                                                                  | `UPI_NOT_SET_UP`                                                                                         |
| `tenders.confirm`    | `{ tenderId, reference }`                     | `{ resolution }`                                                                        | `ALREADY_RESOLVED`, `DUPLICATE_REFERENCE`, `NOT_PENDING`                                                 |
| `tenders.replace`    | `{ tenderId, mode, reference?, approvalId? }` | `{ resolution }`                                                                        | `ALREADY_RESOLVED`, `CREDIT_NEEDS_PARTY`, `APPROVAL_REQUIRED`, `APPROVAL_INVALID`, `DUPLICATE_REFERENCE` |
| `tenders.pendingUpi` | `{ from?, to? }`                              | `{ tenders[{ billNo, amountPaise, billedAt }] }` (for 005 day-close and 010 Today card) |                                                                                                          |

**Replacing a pending UPI tender with credit** runs the same checks as a credit tender in `bills.save`: the bill needs a party (`CREDIT_NEEDS_PARTY`), and an amount over the party's credit limit (004) needs an approval (005): the first call returns `APPROVAL_REQUIRED`, and the retry passes `approvalId`. One transaction inserts the `tender_resolution` row, writes the party ledger debit through 004's `PartyLedgerPort` and consumes the approval; if any part fails, nothing is written. A replacement by UPI claims its reference in `upi_reference`.
